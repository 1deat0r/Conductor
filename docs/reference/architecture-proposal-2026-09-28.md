# Superset successor — reviewed architecture proposal

Design date: 28 September 2026. Horizon: production foundations for 2027. This is a proposed architecture, not an implemented system or a guarantee about future standards. Working name: **Conductor**; this is an internal label, not a cleared product name. Assumption: a focused team of 12 engineers plus product/design and security support, building for individual developers and small-to-medium engineering teams before very large enterprise fleets.

**1. The product I would build.** A local-first development workbench with durable agent execution, explainable permissions, reproducible environments, and first-class Linux, Windows, macOS, Android, and iPhone clients. The primary unit is a task that produces a reviewable change, not a terminal tab. A task has a goal, repository and base revision, owner, execution attempts, context references, spending/time/resource limits, approvals, and verified outputs. A terminal is one way of interacting with an attempt. Multiple agents are useful only where their work can be isolated and integrated economically.

**2. Evidence and starting point.** I inspected Superset commit `3b602411ee635a2934977b628f12cc09b30727e4`, dated 27 September 2026 at 16:05:35 −07:00, which is 27 September at 23:05:35 UTC and 28 September in Auckland. Its README already describes worktrees, agent terminals, review, browser previews, remote access, automations, CLI/SDK/MCP, and an iPhone client. It lists Linux as experimental and Windows as unavailable. The repository has an Electron frontend, Expo mobile app, separate host-service and PTY daemon, local SQLite, tRPC, and a Cloudflare relay; mobile contributor instructions explicitly say iOS-only. Therefore separating the UI from execution is already present in Superset. The proposed successor strengthens the contracts and guarantees around that separation rather than presenting it as a new discovery. The repository's cloud-sandbox design notes also document identity, lifecycle, credentials, and cost complications; these are evidence of design tradeoffs, not a claim that every historical problem remains unfixed.

Sources: [pinned README](https://github.com/superset-sh/superset/blob/3b602411ee635a2934977b628f12cc09b30727e4/README.md), [host entry point](https://github.com/superset-sh/superset/blob/3b602411ee635a2934977b628f12cc09b30727e4/packages/host-service/src/serve.ts), [PTY entry point](https://github.com/superset-sh/superset/blob/3b602411ee635a2934977b628f12cc09b30727e4/packages/pty-daemon/src/main.ts), [mobile scope](https://github.com/superset-sh/superset/blob/3b602411ee635a2934977b628f12cc09b30727e4/apps/mobile/AGENTS.md), [sandbox design](https://github.com/superset-sh/superset/blob/3b602411ee635a2934977b628f12cc09b30727e4/docs/cloud-sandbox-mismatches.md).

**3. Overall shape.** Three logical planes: interaction, coordination, and execution. Desktop/mobile/web/CLI belong to interaction. An optional coordination service owns team identity, device enrollment, project membership, task assignment, remote command delivery, billing, and notifications. A host daemon owns workspaces and attempts on an actual execution machine. The host authorizes each action and delegates execution to an appropriate sandbox. Locally, the desktop reaches the daemon directly with no cloud account requirement. Remotely, clients reach a cloud or self-hosted gateway, and enrolled hosts establish outbound authenticated connections. The same host contract covers a personal laptop, Linux server, macOS build machine, Windows machine, and managed ephemeral worker. Host capabilities differ explicitly.

This starts as a modular product, not a fleet of microservices. Initial deployment consists of desktop/mobile clients, one Rust host distribution, one TypeScript control application with API and worker processes, Postgres, object storage, and a separately scalable connection gateway. A runner pool is added for managed execution. Identity and push delivery use existing platform services.

**4. Stack decisions.** Desktop: Electron, React and TypeScript, Monaco for editing/diffs, xterm.js for terminals. Mobile: React Native with its current supported architecture, Expo development builds/native projects, Swift and Kotlin modules where platform integration requires them. Host: Rust, Tokio, SQLite in WAL mode, platform PTY APIs, Git CLI. Coordination: TypeScript on a supported Node.js LTS, Fastify, Postgres, SQL migrations, S3-compatible object storage. Interfaces: versioned OpenAPI/JSON Schema for commands/events and generated TypeScript/Rust SDKs; WebSocket for bidirectional subscriptions and terminal streams. Telemetry: OpenTelemetry and an exporter chosen by deployment. Monorepo: pnpm workspace and Turborepo for TypeScript plus a Cargo workspace. Exact dependency patches are selected and locked at implementation time, with automated upgrades, rather than treating today's versions as a 2027 architecture.

Electron has a memory/distribution cost, but its consistent Chromium behavior is valuable for a terminal/editor/preview-heavy desktop. Tauri remains a possible later architecture experiment, with a real migration cost; its use of different platform WebViews adds a testing variable today. React Native shares domain models, networking, localization, and design tokens with desktop, not DOM components or the desktop layout. Rust is restricted to the execution substrate, where process lifetime, filesystem handling, streaming, and resource accounting justify it. TypeScript retains product iteration speed. A clean implementation can use this split immediately; migrating a fork would keep working TypeScript host modules behind the new contract until Rust replacements pass behavior tests.

References: [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Tauri WebViews](https://v2.tauri.app/reference/webview-versions/), [React Native architecture](https://reactnative.dev/architecture/landing-page).

**5. Desktop architecture.** The Electron main process owns windows, OS integration, menus, file dialogs, updates, and a narrow IPC bridge. It does not own task lifetimes. The trusted renderer loads packaged application code, has Node integration disabled, runs sandboxed with context isolation, and can invoke only schema-validated operations. The bridge verifies sender and frame, bounds message sizes, and passes commands to the host. Browser previews run in separate sandboxed WebContentsView instances with distinct session partitions and no privileged preload. Navigation, downloads, external schemes, camera, microphone, and clipboard require explicit policy. Untrusted markdown, diffs, terminal hyperlinks, and attachments are rendered as hostile data. Workspace preview origins and product authentication origins are separated.

The workbench has a task inbox, task detail, workspaces, editor/diff, terminal, previews, evidence, and an approvals queue. Show evidence freshness and why a task is blocked. Virtualize logs and file lists, lazily start Monaco language services, and limit active GPU terminals. Search and task navigation must remain responsive with hundreds of historical tasks even when only a bounded number run simultaneously. Integrate external editors and LSP/DAP where useful; do not promise immediate compatibility with the entire VS Code extension ecosystem. Accessibility, keyboard remapping, localization, screen-reader testing, and high-contrast themes are release requirements.

Browser isolation includes default-deny permissions and popup policy, constrained custom protocols and network-level controls for loopback/private destinations. Product IPC is never exposed to previews. Authenticated browser automation receives a separate, coarse account-session grant: a website may allow writes within that session without consulting the tool broker. The interface must say so.

**6. Linux, Windows, macOS are separate release targets.** Linux uses POSIX PTYs, user-scoped systemd where available, inotify, and deb/rpm/AppImage packaging; test Wayland and X11, multiple distributions, file dialogs/portals, and GPU-disabled fallbacks. macOS uses POSIX PTYs, launchd user agents, FSEvents, Keychain, Developer ID signing and notarization, and Apple Silicon plus supported Intel builds. Windows uses ConPTY, named pipes with user ACLs, Job Objects for process-tree control, ReadDirectoryChangesW, Credential Manager/DPAPI, signed installers, and native PowerShell/Git tooling. The host normally runs as the logged-in user; a boot-time service is an explicit installation mode because it changes sessions and credential access.

WSL2 is an additional Linux execution target registered as a different host, not an assumption that every Windows command is Bash. Keep repositories on the target's native filesystem. Translate paths only at declared boundaries; preserve case semantics, symlinks, executable bits, Unicode filenames, long paths, and line-ending policy. ARM64 artifacts enter the same contract suite before being advertised. Record the host's OS/architecture/toolchain in every result, because a Linux passing build does not prove a Windows or iOS result. [Microsoft ConPTY](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session).

The proposed initial qualification matrix is finite. These are target tiers, not claims that builds already exist. Exact framework/OS compatibility is proved in the first spike, and an OS leaving security support leaves the supported matrix even if a binary still launches.

| Target | Initial qualification scope | Distribution and execution |
|---|---|---|
| Linux desktop + owned host | Primary: Ubuntu 24.04/26.04 LTS x64; Wayland on both, X11 on 24.04 | deb and AppImage; POSIX shells; user systemd where available |
| Windows desktop + owned host | Primary: Windows 11 x64, supported editions on 24H2 or newer | Signed installer; ConPTY/PowerShell; user-session supervisor |
| macOS desktop + owned host | Primary: Apple Silicon, macOS 15 or newer while supported | Signed/notarized app; launchd; explicit shell/toolchain profile |
| Android | Primary: Android 12+ ARM64 devices with Google services | Play-distributed native app; FCM optional for correctness |
| iPhone | Primary: iOS 18+ on framework-compatible supported devices | App Store native app; APNs optional for correctness |
| Additional configurations | Beta after qualification: Intel Mac, Windows ARM64, Linux ARM64/Fedora, WSL2 host, Android without Google services | No implicit parity claim; Google-free Android uses foreground inbox refresh |

Each primary OS gets installed-binary CI and dedicated physical hardware; iPhone and Android each cover an oldest-supported and current reference device, with an additional Android manufacturer. Platform owners publish exact tested OS/architecture/adapter combinations per release. Linux package repositories and AppImage update metadata have their own signed update paths; do not assume Electron's macOS/Windows updater handles Linux. Missing Git, agents and credentials are a first-run diagnostic, with visible executable paths/versions and selected environment profile. Background discovery never silently executes arbitrary shell startup files. Trusted host mode has the effective authority of that OS account; credential stores do not defend against every malicious process running as the same user.

**7. Mobile is an operational client.** Android and iPhone both support creating tasks on available hosts, attaching context, reading summaries and paged logs, inspecting diffs, commenting, answering agent questions, approving eligible actions, pausing/cancelling work, and opening private previews. Editing is optimized for small patches and review; an advanced foreground terminal is optional. A phone never needs to execute an arbitrary repository toolchain. iOS builds still require macOS hosts; Android builds require suitable Android tooling on an advertised host.

Use APNs on iOS and FCM on Android as best-effort wake/attention hints, not the authoritative event bus. A notification contains an opaque task reference and a minimal generic message, no source text, secrets, or approve token. On foreground, fetch current authorized state and resume from a stored event cursor; a persistent server inbox makes missed pushes harmless. SQLite caches recent authorized snapshots, encrypted with an app key held in Keychain/Keystore; apply retention limits and clear on sign-out. Background work is opportunistic, with platform APIs and bounded refresh, never a perpetual socket or agent loop.

Queue offline draft prompts/comments only with base revisions, expiry, and an explicit pending state. Do not silently submit an offline approval later. Present exact command/tool arguments, repository, affected resources, estimated cost, and the digest of the proposed action. Send approval only after fetching its current revision. Reauthentication/biometric unlock protects the device key for sensitive actions; biometrics alone do not prove what was approved. Make Android parity a release gate, not a framework assumption. Support screen readers, dynamic text, Android back navigation, deep links, and network transitions on real devices. OS minimums follow security support, framework requirements, and measured users, rather than inheriting Superset's iOS-only cutoff. [Android background restrictions](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions).

Mobile approval uses a canonical, versioned structured representation in trusted native UI. It shows organization, actor, host, repository, immutable inputs, destination, scope and expiry; safely escapes bidi/control characters; and rejects unknown fields/schemas rather than hiding them. If an effect cannot be explained completely on the phone, require desktop review. A deep link can open a request but cannot approve it. Refetch after resume and show the durable receipt, rejection or still-pending state after submission. Mobile previews use a separate WebView without a sensitive native bridge or product cookies, with constrained navigation, downloads and schemes; approval controls are never inside it.

Use an encryption-capable native SQLite build, qualified in the spike, covering the database, WAL/temp data and attachment cache. Cache encryption and approval/device keys are separate. Approval keys require foreground user presence; replaceable caches use a bounded offline-read policy (proposed default 24 hours for team source, configurable shorter). Sensitive caches and credentials are excluded from cloud/device-transfer backups; app-switcher snapshots conceal sensitive content. Key invalidation, biometric changes, reinstall or unsafe restore require fresh authentication/enrollment; missing cache keys cause a visible cache reset. Unsent drafts have a separately defined local retention/export/recovery path and are never silently discarded as cache. Revocation cannot erase an offline phone or already exported data. [Apple background delivery](https://developer.apple.com/documentation/UserNotifications/pushing-background-updates-to-your-app), [Expo key-storage lifecycle](https://docs.expo.dev/versions/latest/sdk/securestore/).

**8. Host runtime.** The eventual host subsystem covers the authenticated command server, workspace manager, scheduler, policy evaluator, tool/credential brokers, artifact store and sync client, with adapters and indexing in separate workers. These are module boundaries first; the initial Rust scope is narrowed below. Agent adapters and third-party integrations execute outside the daemon. A small per-user process supervisor owns PTY handles and child job groups; it stays alive across UI and host-control restarts, so a control upgrade can reconnect to live sessions. Supervisor upgrades drain sessions by default. Host reboot or supervisor crash is not transparent live-process recovery: the UI reports interruption and offers resume from a recorded checkpoint if that adapter supports it.

A bounded PTY ring buffer handles interactive replay; disk-backed chunk files retain configured history. Control messages and terminal bytes have separate flow-control channels so a compiler dumping gigabytes cannot block cancellation. Output truncation is visible. Backpressure, storage quotas, and subscription filters bound memory/disk. Only one writer holds the terminal input lease; collaborators can observe and request takeover, preventing interleaved typing. OS-level locks and a host epoch prevent two daemons adopting the same workspace accidentally.

The supervisor exposes idempotent `Start(session_id, launch_digest)`, query and cancel operations. It persists launch intent and exit receipts, rejects reuse with different payloads, and authenticates controller adoption with a host incarnation. After an ambiguous reply the controller queries/adopts; it never blindly spawns again. A crash between an OS spawn and a durable receipt may still be unknowable: report interruption/unknown outcome and require a new explicit attempt if nonexecution cannot be proved. PIDs alone are insufficient. Possibly executed terminal input is never automatically replayed after reconnect.

| Lifecycle event | Interactive-user installation contract |
|---|---|
| Close window, UI crash or normal Quit | Execution continues while the user session and supervisor remain available; expose a separate Stop host action |
| Control process crash/update | Supervisor retains PTYs; controller reconciles and adopts; temporary UI disconnection |
| Supervisor update | Drain by default; user-authorized interruption if a forced security update cannot wait |
| Supervisor crash | Running-state uncertainty; recover receipts/output and report interruption; no transparent resume claim |
| Sleep | Machine execution suspends; provider/network operations can time out; reconcile on wake |
| Logout or reboot | Interactive execution is interrupted; retained checkpoint/output only |
| Uninstall | Stop managed processes under a visible uninstall policy; offer export/retention of user data |

An unattended-host installation is a separate explicitly enabled profile with boot/session-independent supervision and separate credential provisioning. No silent Linux lingering or system-service enablement. Windows Job/ConPTY ownership and shutdown must be qualified per supported OS; the supervisor owns the relevant handles, not Electron. Keep supervisor receipts in a separately owned schema so controller migration cannot corrupt an active writer. Rust begins with supervision, filesystem/workspace control, durable host state and enforcement; provider adapters and expensive indexing run in isolated workers. Reserve control capacity so heavy logs cannot starve cancellation even when CPU or disk is saturated.

**9. Domain and storage ownership.** Distinguish `Task`, `Attempt`, `Workspace`, `Host`, `Environment`, `Session`, `Action`, `Approval`, `Artifact`, and `IntegrationOperation`. A task can have multiple attempts but each attempt has one execution owner. A workspace identifies a repository snapshot and writable checkout, not a machine. A host is a registered execution endpoint. An environment is an immutable toolchain/image description. A session represents an adapter-specific conversation or PTY and is not assumed portable.

Host SQLite owns local workspace records, attempt state, command inbox/deduplication, action receipts, terminal offsets, and sync outbox. Filesystem/Git stores working files, checkpoints and blobs. Control Postgres owns organizations, devices, membership, task requests/assignment, online authorization, budgets, notification inbox, and remote projections of host execution. Blob storage holds explicitly uploaded logs/artifacts and managed-runner checkpoints. Mobile stores replaceable projections. Never copy an entire live SQLite file through a sync service or let cloud and host independently edit the same state field. Local-only tasks acquire a globally unique identity on creation and are explicitly published if collaboration is enabled.

A durable event records `event_id`, aggregate ID, aggregate sequence, schema version, causation/command ID, actor, host epoch, and timestamp. Order exists per aggregate, not as a fictitious global total order. Business state changes and their outbox rows commit together. Client projections replay events or reload snapshots after a cursor expires. Use ordinary relational current-state tables plus append-only operational events; avoid forcing every UI preference into full event sourcing. Large tokens, terminal bytes, and files are chunked separately. Proposed defaults: 7 days local terminal retention, 30 days hosted logs, longer compact audit metadata, all configurable by organizational retention policy. Redaction happens before telemetry upload; paths and prompts are private by default.

Authority is assigned by field and aggregate, not inferred from where a copy happens to be stored:

| Record | Authoritative writer | Command/revision rule |
|---|---|---|
| Local task intent and schedule | Origin host | Host task revision; publishing creates a remote projection, not a second writer |
| Team task desired state and assignment | Coordinator | Task revision in Postgres; desktop changes route here |
| Attempt observed execution and receipts | Assigned host/supervisor | Attempt revision plus ownership generation; cloud is a projection |
| Protected external-operation admission | Credentialed broker | Serialized operation ledger and current ownership/policy |
| Terminal input ownership | Supervisor | One input lease; explicit takeover |
| Client preferences/cache | Device | Never determine execution authority |

A team task's local emergency stop terminates its attempt even while disconnected; it is recorded as an observed safety stop, not a competing write to team task intent. Re-running requires a distinct authorized attempt. Cloud acceptance of a queued command can later yield a durable host rejection for stale state. Cancellation intent and confirmed cancellation are separate fields. Promoting a local task to coordinator ownership requires an explicit quiescent authority transfer or creation of a new team task linked to the old one. Task progress is derived from desired state and attempts, not one scalar updated by both stores.

Critical SQLite command/receipt/outbox transactions use WAL with `synchronous=FULL` on supported local storage; disk-full/I/O failure prevents acknowledgement. Lossy terminal history is separate. SQLite backups use its supported online-backup mechanism, not a raw live-file copy. [SQLite durability](https://sqlite.org/pragma.html#pragma_synchronous), [backup API](https://www.sqlite.org/backup.html).

Artifact manifests bind tenant/project/task/attempt, producer, trust class, content hash, media type and access/retention label. Authorize upload finalization, reads, indexing, previews, sharing and restores; an object ID or hash grants no access. Cache/blob namespaces include trust domain; do not expose cross-tenant existence via deduplication. Short-lived signed URLs have a stated revocation delay; use an authenticated delivery gateway where immediate new-read revocation is required. Logs remain confidential even after redaction.

**10. Commands and durability.** Commands include `command_id`, task/attempt ID, expected aggregate revision, actor/device, desired operation, deadline, and payload digest. Clients keep their pending command until they receive a durable acknowledgement. The coordinator persists before acknowledging, delivers at least once, and the host deduplicates transactionally. A lost reply does not mean an operation failed. The host records accepted, started, and resolved status separately and sends resumable events. A host offline after cloud acceptance yields “queued for host,” not “running.” A cancellation request is pending until the process owner confirms it, and does not undo already completed external effects.

Internal state transitions can be transactional; network tools cannot generally be exactly once. For a forge API call, persist an intent and stable operation ID, use provider idempotency where available, and reconcile remote state after an ambiguous timeout before retry. If the provider cannot prove whether a non-idempotent operation happened, mark it `outcome_unknown` and request reconciliation rather than automatically replaying it. Attempt execution uses the following state machine (task progress is a derived projection, as defined in §9): `draft → queued → provisioning → running → waiting_for_input/approval → validating → review_ready → completed`, with explicit failed, cancelled, and interrupted states. Completion means recorded acceptance criteria met; an agent's “done” message alone only ends its turn.

Acknowledgements are explicit: `coordinator_stored`, `host_accepted`, then `effect_resolved`. Each command ID is bound to one immutable payload. Set a bounded offline submission/replay horizon (proposed 7 days); persist tombstones beyond that horizon, keep external-operation identities for their reconciliation/retention period, and reject expired commands even after receipt cleanup. An older client refreshes state rather than generating a new ID to blindly replay old intent. Local-first means independent of the coordination service; a remote model still needs its provider connection.

**11. Offline, split ownership, and handoff.** A local attempt remains owned by its host during disconnection and can continue within its previously authorized scope and budget. The cloud must not start a duplicate merely because a heartbeat expires. High-impact new actions needing current team policy stop while disconnected. Authoritative revocation stops new protected admissions and closes affected streams/input leases; already-dispatched effects may still complete. Disconnected grants expire under their stated limits; instantaneous offline revocation is impossible. Never label presence as certainty: show last observed time and distinguish unknown, offline, asleep, provisioning, and failed.

A cooperative transfer requests a quiescent point, revokes the old input lease, checkpoints tracked and explicitly included untracked files, records environment/context manifest and artifact hashes, and acknowledges source shutdown before a new execution epoch is granted. If the source is unreachable, create a visibly separate recovery attempt from the last durable checkpoint. Do not claim process migration, unsaved-memory recovery, or preserved provider conversations when unsupported. External write effects require a currently valid fenced grant at the broker; a stale isolated attempt may calculate locally but receives no new publication admission. Already-dispatched operations require the reconciliation rules below. Credentials that bypass that broker weaken the guarantee and disqualify an unmanaged attempt from automatic failover.

Fencing has three separate jobs: reject new stale admissions, deduplicate one operation, and prevent conflicting writes to the same external resource. The broker is the sole credentialed route for those guarantees. Its epoch validation and durable intent registration serialize with handoff. Closing old admission cannot recall an already-dispatched API call. Transfer reconciles outstanding calls; use provider conditional writes/resource versions where supported. Otherwise an unresolved prior effect blocks conflicting publication by the recovery attempt. Recovery may compute on a separate branch while publication remains blocked.

Offline grants identify permissible operations, budget allocation and expiry. Proposed defaults: protected publication always needs online authority; limited managed computation can use a 15-minute grant renewable while connected; ordinary local-only trusted tasks use local authority. Expiry uses a bounded server-issued lifetime and monotonic tracking; restart, clock rollback or uncertain elapsed time fail closed for protected actions. Queue acceptance never bypasses current membership/policy on reconnect. Externally usable credentials carry their own revocation limits and exclude the run from strong automatic-failover guarantees.

**12. Orchestration and schedules.** Start with a persisted task DAG and bounded scheduler. Agents may propose a plan, but policy and the user determine which edges can execute. Independent tasks get independent checkouts. Use one integration queue per target branch to apply a candidate to the latest base and rerun required checks. Failures invalidate affected downstream evidence. Keep the scheduler deterministic about dependencies, resource limits, priority, fair tenant shares, retry classes, deadlines and maximum depth; the language model supplies reasoning, not the authoritative state machine.

Automations have an IANA timezone, schedule revision, DST rule, missed-run policy, concurrency key and maximum runtime/cost. Persist a unique occurrence ID so a restart does not duplicate an invocation. Default to skip or coalesce missed occurrences rather than storming through a backlog. A local schedule belongs to one host; a team schedule belongs to the coordinator. Moving ownership is explicit. Postgres/SQLite transactions, leases and outboxes suffice initially. Introduce a workflow engine only when operational complexity proves a need, and use it as the owner of that workflow rather than duplicating the scheduler's authority. A broker/stream service is a scale option, not the first source of truth.

**13. Agent and model portability.** Define an internal adapter contract: discover capabilities, start, send input, emit normalized events, cancel, checkpoint/resume if supported, request tools/permissions if supported, and report usage if available. Preserve vendor payloads in bounded redacted diagnostic records so useful features are not erased by normalization. Use Agent Client Protocol where supported, native provider SDKs for richer structured control, and a PTY fallback for arbitrary CLI agents. MCP supplies tool/resource integration; it does not replace editor-agent lifecycle, task scheduling, or authorization. Version both adapters and their capability manifests. “Resume supported” must specify same host, new host, same agent version, or portable context only. [ACP overview](https://agentclientprotocol.com/protocol/v1/overview).

Model selection uses task requirements, data residency, context budget, measured quality, availability, latency and price. A cheap model may summarize a diff while a stronger one handles an uncertain design. Do not hardcode a model family into task schema or automatically send confidential context to a fallback provider. Pin the selected model identifier and adapter version per attempt. A model upgrade creates a new evaluated option rather than silently changing historical reproducibility. BYO credentials use the user's authorized provider path; no assumption that a subscription entitles arbitrary remote API use. Usage is exact where providers report it and visibly estimated/unavailable for opaque CLIs.

**14. Workspaces and environments.** A workspace manifest includes repository identity, base SHA, branch, environment digest, mounts, network policy, secrets references, allowed setup commands, ports, architecture and OS requirements. Use Git CLI as the compatibility boundary and serialize operations touching shared repository metadata. Worktrees are efficient for trusted local parallelism; they share repository internals and are not security isolation. An isolated untrusted run receives a separate clone/snapshot and private Git directory, not a writable shared `.git` mount. Do not copy arbitrary hooks or run setup scripts automatically on opening an unknown repository. Submodules, LFS, ignored files, untracked files, and symlinks have explicit handling. [Git worktrees](https://git-scm.com/docs/git-worktree).

OCI images and Dev Container configuration are portable environment inputs on suitable Linux runners, not a promise that a Linux container can build every native project. Native macOS and Windows host pools remain necessary. Dependency caches are keyed by lockfile, toolchain, OS/architecture and trust domain, with no cross-tenant writable cache. Allocate ports through the host instead of scanning and assuming free ports. Workspace deletion follows a recoverable archive/checkpoint path with an explicit policy for ignored files; quotas drive warnings and user choices rather than silent removal of valuable work.

The privileged daemon does not run ordinary Git commands on guest-controlled repository metadata. A confined inspection helper sanitizes environment/configuration, disables hooks/fsmonitor/external diff/textconv/pagers, restricts transports and has no ambient credential helper. Fetch/submodules/LFS/checkout are separately authorized execution. Never apply global `safe.directory=*`. Import reconstructs repository metadata from validated objects/manifests instead of activating saved arbitrary Git configuration. Archive/patch extraction rejects traversal, device files, escaping links and Windows reparse/alias tricks. App locks serialize app-owned Git operations; external trusted tools can still race and require detection/reconciliation. [Git configuration](https://git-scm.com/docs/git-config).

Checkpoints transition `creating → verified → published → cleanup_allowed`. Upload immutable content-addressed objects, verify their completeness, then commit the manifest/reference event. A published checkpoint is required before automated source destruction or transfer; failed uploads leave the source intact. Reference-aware garbage collection has a grace period for orphan uploads. Retain a compact change package independently of verbose logs (proposed 180-day hosted default, configurable); local-only host loss has no backup guarantee unless backup/export was configured. Export includes the manifest, Git data/patches, allowed artifacts and environment description with credential references to rebind; test import into a fresh host.

**15. Isolation and permissions.** Offer three clearly labeled modes: trusted host execution for user-selected code; restricted local execution for supported container/VM environments; and isolated managed execution for unattended or untrusted jobs. Linux containers use namespaces, cgroups, seccomp, reduced capabilities and brokered mounts/egress, but are not advertised as the strongest hostile-tenant boundary. Managed multi-tenant execution uses a per-workspace VM/microVM under an established provider, with no control-plane credentials inside the guest. Firecracker is a Linux/KVM implementation option, not a universal macOS/Windows sandbox. macOS/Windows users can use a managed Linux VM for compatible workloads; native workloads use dedicated appropriately isolated machines. [Firecracker](https://firecracker-microvm.github.io/).

Policy applies to filesystem roots, command/tool classes, network destinations, credentials, publications, device/browser operations and budgets. Model-suggested arguments are untrusted. Verified managed execution profiles route protected operations through a broker, whose policy check and short-lived capability grant bind the action digest, workspace revision, tenant, actor, target, host epoch, policy revision, nonce and expiry. Revalidate immediately before effect and reject stale grants. A process with arbitrary shell and network access can bypass a per-tool UI, so arbitrary CLI support exposes coarse sandbox permissions, not a false claim of per-command enforcement. Repository text, a web page, MCP output and a skill file cannot grant themselves more authority.

“Managed” means a tested execution profile, not merely a structured adapter. All repository-derived programs, including adapters, setup scripts, LSP/DAP servers, build/test processes and descendants, stay inside that profile. The guest cannot access control sockets, policy/audit stores, device keys, Docker sockets, SSH agents, cloud metadata or ambient user credentials. A broker outside the workload authenticates an attempt-scoped identity that cannot impersonate a desktop or approver, and exposes typed operations only. Network restrictions cover direct IP and DNS paths outside the guest. Unsupported restrictions cause rejection or an explicitly selected trusted-host mode; never silently downgrade isolation.

The canonical Action includes schema/version, broker audience, tenant/actor/device, attempt and ownership generation, tool/executable identity, working directory, environment policy, exact arguments, immutable input hashes, normalized destination/resource, policy revision, nonce and expiry. UI description and execution parameters derive from that same object. Single-use approval consumption and intent registration are atomic. Snapshot mutable scripts/configuration or use safe handles; a dirty worktree, untracked-file change or symlink swap invalidates relevant approvals. A generic shell grant authorizes its stated sandbox scope, not an impossible guarantee about shell meaning.

Managed native macOS/Windows capacity is tenant-dedicated or reprovisioned from a verified clean image between trust domains. Stopping a process or deleting a checkout is insufficient. Revoke job credentials, discard user profiles and writable caches, and admit reuse only after the reset guarantee is tested. A VM snapshot never restores a live approval, credential or execution lease. An allowed network endpoint may itself permit data exfiltration, so provider/browser grants also specify what data may leave the workspace.

**16. Identity, credentials and remote connectivity.** User authentication uses a standards-based OIDC provider with PKCE and optional enterprise SSO. Device enrollment creates a per-device key, confirms an expiring pairing challenge, binds tenant and role, and supports revocation/rotation. Local sockets have owner-only permissions; Windows pipes have explicit ACLs. Local credential storage is in the OS store and fails visibly if unavailable, rather than storing plaintext as fallback. Hosted secrets are encrypted under KMS with separate tenant and service access policy. Prefer short-lived provider tokens and scoped Git forge credentials. Never persist secrets in Git remote URLs, command-line arguments, logs or push payloads.

Hosts initiate mTLS connections to the gateway, supporting corporate egress restrictions without opening inbound machine ports. Use HTTP commands and resumable WebSocket event/PTY channels first; a QUIC or direct LAN transport can be added behind the same framing after measurement. The gateway routes by authenticated tenant/device/host, checks authorization for each stream and command, uses bounded queues, and treats reconnects as normal. HTTPS preview access uses a separate registrable content domain, short-lived workspace/port-scoped tickets, and a backend routing map that prevents arbitrary private-network destinations. Never forward product cookies or grant a preview shell privileges.

Choose a clear data model: hosted team mode is a trusted service, encrypting transport and stored data but able to read authorized team artifacts. Local-only mode keeps source and transcripts on the host except provider requests the user chooses. Self-hosted mode relocates the coordination/storage services. End-to-end encrypted opaque relay mode is a potential separate feature with different search, indexing, recovery and multi-device key-management costs; do not market normal TLS as E2EE. [MCP security practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).

Keep user, approving device, host, workload and integration identities separate, with distinct token audiences and privileges. Pairing binds account/tenant and the new public key to an expiring nonreplayable challenge; a device cannot assign its own role. Verify token/key bindings, issuer, redirect and audience, with refresh-token rotation or sender constraints as appropriate. Hosts do not share an organization-wide master secret. [OAuth security BCP](https://www.rfc-editor.org/info/rfc9700/).

Preview routes bind tenant/workspace/user, host epoch, namespace, service instance and route generation, not merely a reusable port. Single-use ticket redemption creates a scoped session; secrets are not forwarded to the preview app and are suppressed from logs/referrers. Use host-only cookies, origin/CSRF checks and authenticated WebSocket admission across sibling workspace origins. A shared parent domain is not sufficient cross-workspace isolation. Route changes, stop and revocation invalidate sessions; ignore upstream attempts to override routing/authentication headers.

**17. Context, memory and retrieval.** Context assembly operates under repository/tenant permissions. Begin with ripgrep, Git diff/history, file maps, parser/LSP symbols and SQLite full-text search. Add embeddings only if evaluation shows a gain; keep the embedding model/index format replaceable and keep private corpora separate. Every context item records its origin, revision/hash, capture time, access label, and expiry. A task receives bounded references and excerpts, not an ever-growing global chat transcript. Mark content stale when its source changes. Summaries are derived artifacts with provenance and can be regenerated.

Task memory lasts for a task; project knowledge is explicitly retained and reviewable; personal preferences are separate. Agent-generated claims remain tentative until promoted with evidence. A malicious comment must not become a durable instruction for later tasks. Access filtering occurs before retrieval and again before model submission. Deleting a source invalidates its summaries/index entries and eventually its backups under retention policy. No shared vector search that leaks another tenant's filenames or snippets. Local inference is another provider adapter with resource capabilities; it never silently occupies the GPU needed by the user's work.

**18. Review, integration, and forge operations.** An attempt produces a change package: base SHA, patch/commit, environment digest, adapter/model identifiers, test commands and results, logs, screenshots or preview artifacts, and provenance. A reviewer sees what was executed, on which platform, with which policy, and which checks were skipped. Test code from an untrusted PR is itself untrusted execution. Run it with the same isolation discipline. Require fresh validation of the integrated candidate, since separately passing agent branches can still conflict semantically.

Forge adapters isolate GitHub/GitLab/etc. differences. Short-lived app tokens and explicit operation intents cover PR creation, comments, pushes and merges. Branch protections and required reviews remain authoritative. Permission to edit code does not implicitly authorize production deployment or writing messages. Auto-merge is a separate configured policy tied to the current candidate SHA and checks; a changed patch revokes stale approval. Agents reviewing their own output are supplemental evidence, not an independent assurance substitute. Cross-agent review can intentionally use different prompts/providers but still needs executable checks.

Label evidence by its producer: workload claims, supervisor-observed exit status, or an independently controlled validation job. A guest cannot sign the controller's attestation; a content hash proves byte identity, not truth. Untrusted PR tests and caches cannot silently become trusted release inputs. Active HTML/SVG evidence uses the untrusted-content surface; restoring a result begins in a new isolated workspace. Integration queues key by repository and target ref, bound rebase retries, and expose starvation instead of looping forever.

**19. Plugins and browser tools.** Ship signed, versioned plugin manifests declaring capabilities, compatible protocol ranges and entry points. Declarative skills are read-only data until granted authority; executable plugins run out of process, with resource and filesystem/network limits. UI extensions use sandboxed frames with a narrow typed bridge. Start with a curated first-party registry rather than arbitrary privileged code in the renderer. MCP servers are one connector type and use correctly scoped downstream authorization; MCP endpoints reject tokens not issued for their own resource audience. Downstream integrations use separately authorized, narrowly scoped credentials; tenant and actor come from authenticated state, never model arguments. Remote URL handling must resist SSRF, redirects to internal services, and DNS changes. Browser automation runs with task-specific profiles and trace artifacts, with explicit access to authenticated user sessions; no accidental reuse of a personal browser cookie jar.

**20. Cloud operation and economics.** Start in a single selected home region per tenant with multi-zone managed Postgres, versioned object storage, API replicas, a durable worker, and gateway replicas. The control plane does not run repositories. The runner provider manages isolated compute; an internal `RunnerProvider` contract covers create/start/stop/snapshot/destroy/capabilities/cost. Use tagged resources, expiry, idempotent provisioning and a reconciler that finds orphan VMs/volumes after partial failure. Scale job execution by admission control and actual CPU/RAM/IO capacity, not by “100 agents” marketing. Managed Apple builds and GPU workloads require explicit pools and quotas.

Meter model use, compute seconds, storage and egress separately. Reserve a budget before launching a task, reconcile reported usage, stop issuing new work as limits approach, and report possible in-flight overshoot. Opaque subscriptions cannot support exact per-token billing; show time/resource budgets and uncertainty. Local and remotely allocated budgets must not both spend the same reservation. Charge optional hosting/team services without making local work dependent on a metering server. A self-hosted package includes control application, gateway, Postgres and object storage; it has a documented manual update/backup path.

Budgets are a durable escrow ledger: allocation IDs are unique, suballocations do not overlap, and states are reserved/committed/released/unknown. Persist local debits before chargeable admission. A disconnected or expired allocation stays encumbered until reconciled or conservatively settled; heartbeat expiry cannot return it to the pool. A recovery attempt needs new funding. Before each model request reserve its conservative maximum bounded by input/output limits; compute has a maximum lease duration and bounded concurrency. Declare an overshoot envelope for in-flight requests, shutdown delay and pricing uncertainty. Without enforceable caps, opaque CLI spending is a soft estimate/time limit, never a hard dollar guarantee.

Idle waiting tasks checkpoint/suspend under an explicit resumability policy, with approval wait time and retained storage visible to the user. Provider-side lifetime caps or an independently operating cleanup path limit control-plane failure cost. Reconcile the provider's complete inventory, including resources missing from the application ledger. Pricing includes warm/idle pools, image pulls, snapshots, retained volumes, failed teardown, egress, database/observability, support and restore drills. Provider idempotency keys retain their full placement/request scope. Do not destroy an idle guest until required artifacts have reached `published`.

**21. Resilience and observability.** Correlate task, attempt, command and action IDs across clients, gateway, host, tool and provider. Record span timings and state transitions, but keep code, prompts, terminal data and credentials out of telemetry by default. Maintain an internal stable event schema and translate to OpenTelemetry; evolving GenAI conventions are an exporter concern. Audit records capture actor, authorization decision, input digest and result reference. Hosted audit exports can use append-only retention controls; a hash chain alone is not proof against an administrator rewriting everything. [OpenTelemetry GenAI conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/).

Initial targets, to validate rather than claim achieved: 99.9% monthly hosted command acceptance; p95 durable acknowledgement under 500 ms in the home region excluding provisioning/provider latency; p95 local task-list navigation under 100 ms after warm load; recovery of acknowledged host commands after forced restart; no duplicate brokered side effects in fault-injection tests where a provider supports deduplication. Proposed managed-storage disaster targets are RPO ≤5 minutes and RTO ≤1 hour, subject to restore drills; an acknowledged database transaction is not automatically a cross-region zero-loss guarantee. Run multi-zone failover drills and off-region encrypted backups, but postpone active-active global writes. If recent state is lost, fence old ownership epochs before dispatching new writes.

Disaster restore enters a write-frozen reconciliation state. Fence the old control and broker deployment, establish a fresh nonreused recovery generation outside the restored snapshot through an independent generation record or deliberate credential rotation, invalidate old grants, and re-enroll affected identities. Do not restore live device/workload authority from a cloned disk. Reconcile the uncertainty window against host receipts, provider state, artifacts and budget allocations before admitting retries or releasing reservations. If revoked membership/consumed approvals cannot be reconstructed, require fresh authorization. A new counter in an old database is insufficient. Test a restored database together with blob manifests, objects and encryption keys; operators resolve unprovable effects rather than automatically replaying them.

Add delivery-delay/queue-age objectives for connected eligible hosts; command-acceptance uptime alone can hide a broken relay. Benchmark on published reference hardware and datasets. Mobile budgets include initial inbox display, paged diff performance, data/battery use and successful completion of create/review/clarify/approve/cancel. Targets remain hypotheses until measurement.

**22. Testing and release engineering.** Contract tests run against all adapters and host targets. Deterministic scheduler/policy tests inject duplicate, delayed, reordered and missing messages, process crashes between intent and effect, approval expiry, device revocation, clock changes and offline reconnect. Filesystem tests cover symlink escape, case collisions, path traversal, permissions and huge repos. Test terminal Unicode/resize/cancellation/survival on every OS. Electron tests cover real packaged binaries; mobile tests cover iOS/Android physical devices, suspended apps, delayed notifications, airplane mode and Wi-Fi/cellular transitions. Run isolation and malicious-plugin exercises before claiming enforcement.

Sign desktop binaries, notarize macOS, sign Windows, and distribute Linux package/update metadata with integrity verification. Separate stable/beta channels; stage rollout, collect opt-in crash metrics, and halt or roll back unhealthy releases. Daemon, adapter and client protocols negotiate features rather than requiring lockstep versions. Support current and previous protocol generations with an explicit minimum supported release window, read-only degraded mode for unsupported clients, and no silent unsafe fallback. Database migrations are backward-compatible expand/contract changes with pre-migration backup and tested recovery; binary rollback alone cannot reverse a destructive migration. Mobile native changes go through app-store delivery; downloaded content must not become arbitrary native plugins.

Publish a compatibility matrix for client↔API, controller↔supervisor, host↔coordinator, adapters and persisted schemas. Target additive client compatibility for at least 180 days unless a security incident forces a shorter window; runtime security support is separate. Unknown display events may be ignored with a refresh path; unknown action/approval schemas fail closed. One owner migrates each on-disk schema and quiesces its writers. Controller updates cannot concurrently migrate live supervisor receipts. New irreversible effects after a backup rule out blind database rollback; use the disaster reconciliation procedure.

Adopt a TUF-style update trust model: signed target hashes/lengths, platform/channel binding, expiry, anti-rollback state, delegated keys, revocation/rotation and a signed recovery path. A security rollback is a newly authorized recovery release. Isolate release signing from repository/PR jobs; attach SBOM and build provenance; keep untrusted contribution caches separate from release caches. Plugin capability expansion requires new policy admission. Assign an emergency update owner and a proposed 48-hour triage/mitigation target for actively exploited critical upstream flaws; do not promise every vendor fix in 48 hours. [TUF metadata](https://theupdateframework.io/docs/metadata/), [SLSA threats](https://slsa.dev/spec/v1.2/threats-overview).

Qualification must break the design deliberately: crash between commit and spawn; delay an API effect across handoff; restore before a successful external write/revocation/budget grant; swap an approved script/symlink; present another tenant's blob ID; poison Git configuration and build caches; contact the daemon from a guest; revoke open terminal streams; replay an old signed update; and force mobile push loss, cache-key loss and account switching. Each claim is tied to exact packaged binary, OS/device, architecture, adapter/profile and test result. These are release gates, not tests performed for this architecture document.

**23. A practical sequence from this date.** Treat dates as planning windows, not GA promises. In the first six weeks of Q4 2026, prove one real task on each desktop OS, both phones receiving its state, a stale approval rejected, live-session survival across UI/control restart, and signed test builds installed. The Q4 exit is an integrated private alpha plus a go/no-go decision. Q1 2027 targets a five-platform beta: trusted local execution, remote access to owned hosts, two structured adapters and PTY fallback, durable task review/steering and eligible approvals. GA follows measured lifecycle, mobile usability/security, store qualification, installation/update recovery and operating drills. Q2 2027 is a possible window for one managed Linux execution provider after the security/durability gates, not a promise to ship every hosting mode. Self-hosting, integration queues, shared native pools and a marketplace each have separate gates and funding. A smaller team defers managed hosting breadth while retaining Android, iPhone and all three desktop OS families.

A plausible 12-engineer allocation is 3 runtime/platform, 2 desktop UX, 2 mobile, 3 coordination/integrations and 2 release/reliability/QA, with shared design and security review. This still needs an on-call/support plan before hosted GA. Owners reassess scope after the six-week proof. Start app-store qualification in Q4 with a real native vertical slice, demo accounts/hosts, signing/push ownership, territories, privacy/account-deletion disclosures and purchase flows. Remote execution does not automatically qualify for any particular store exception. Initial mobile scope excludes downloaded executable plugins and unreviewed native updates; validate Apple and Play distribution policies before committing monetization UX. Store acceptance is an external gate, not a predicted outcome. [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/).

**24. What makes it adaptable in 2027.** Stable task/artifact/action identities outlive model vendors. Capability negotiation allows new agents and transports without rewriting clients. UI lifecycle does not control process lifecycle. Execution is separated from tenancy/control data. Workspaces and environments are portable descriptions with explicit nonportable parts. Permissions are enforced outside the model. Current-state tables and operational journals provide recovery without an unnecessarily universal event-sourcing framework. Vendor adapters, infrastructure adapters and exportable data bound switching cost. OpenAPI/JSON Schema, Git patches/bundles, OCI environment inputs and ordinary object storage keep escape routes concrete. “Future-proof” means tested replacement seams and credible migration paths, not predicting which agent protocol or model wins.

This proposal is not a legal clearance. Open protocol/SDK and export formats are good candidates for permissive licensing even if hosted service implementation is commercial. **26. End-to-end example.** This describes the later full-capability workflow, including managed execution and the integration queue. On an Android phone, create a task against base commit A on a chosen Linux host. The coordinator commits the request and budget reservation, shows queued, and delivers the same command ID until acknowledged. The host verifies membership/policy, provisions a private workspace, commits attempt start, and launches a structured adapter. A requested protected API operation becomes an Action with a digest. The iPhone can fetch its current details and sign an approval for that digest. The host revalidates the policy/revision/epoch before the broker performs the effect. Tests produce artifacts on commit B. Desktop review shows the patch and Linux evidence; if Windows validation is required it dispatches a separate Windows check. The merge queue constructs candidate C against the latest target, reruns required checks, and only then executes the separately authorized forge operation. If connectivity fails after publishing, reconciliation checks the forge before retrying. The task remains inspectable from all clients even after the execution VM is archived.

**27. Independent review and resulting changes.** Three parallel agent reviewers independently evaluated the same completed v1 proposal, covering distributed systems, security and five-platform delivery. They did not author the proposal or consult each other during that first review. Their reviews are preserved separately. This is independent model-session critique, not a human audit or implementation certification. The final design incorporates explicit command/spawn reconciliation, ownership rules, in-flight-effect handling, restore generations, offline budget escrow, published-checkpoint cleanup gates, complete action binding, hostile Git/preview/artifact boundaries, native lifecycle/support matrices and a staffed gated roadmap. All three reviewers rechecked the revised proposal and reported no remaining must-fix design blocker within their scope. The chosen stack remains a recommendation; the strongest guarantees remain conditional on adversarial tests and platform qualification.
