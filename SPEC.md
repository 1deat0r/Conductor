# Conductor implementation specification

Revision: 2026.09.28-4. Design horizon: 2027. Approval status is recorded in `docs/reviews/approvals.json`, bound to the exact review-scope SHA-256. “Approved” means the design is sufficiently specified to implement; it does not certify a working runtime, security, platform compatibility, a delivery date or store acceptance.

## 1. Scope and normative precedence

**R01 — Scope and truthful capability reporting.** Build a task-oriented agent development platform with Linux, Windows and macOS desktop clients and Android/iPhone apps. Individuals can use local execution without a product cloud account; team coordination and managed hosting are optional. Local-first does not make remote models usable without their network connection. Preserve one task/evidence model across clients, not identical layouts. Browser/CLI access is a later surface of the same protocol.

This document, `contracts/`, `docs/decisions.md`, `docs/threat-model.md`, `docs/implementation-plan.md`, `docs/development-workflow.md` and the contributor/enforcement files named by review scope form the reviewed specification bundle. This document takes precedence if their prose conflicts; contradictory normative requirements must be resolved before implementation. `docs/reference/` and conceptual diagrams are historical rationale only. README/STATE/evidence describe what is actually implemented. No Superset code or assets are copied. The owner authorizes a public source repository only after unanimous final specification approval. No open-source license is selected by that authorization; package publication, product licensing/name clearance and release distribution remain separate decisions.

**S0 is the current scaffold.** It provides a packaged-code desktop shell, an Expo Android/iPhone source shell, loopback API health/unsupported-command responses, shared source models, a validated health envelope, Rust host/supervisor diagnostic entry points and local/CI verification wiring. It does not execute agents, persist tasks, create workspaces, expose a relay, enroll devices, collect credentials, authorize actions, implement encryption, provide PTYs, or publish anything. A source build is not five-platform native qualification. Every unavailable feature is visibly unavailable; no endpoint may acknowledge a command it cannot safely execute.

## 2. System boundaries and selected stack

**R02 — Separation of interaction, coordination and execution.** Electron + React + TypeScript own the desktop UI; React Native with pinned Expo native builds owns Android/iPhone. Swift/Kotlin modules implement platform-specific security/lifecycle functions only when needed. Rust owns process supervision, durable host control, workspace operations and the enforcement boundary. Provider adapters and indexing are separate workers. TypeScript/Fastify on supported Node LTS owns team coordination. SQLite owns durable local state; Postgres owns hosted coordination; local blobs/Git and S3-compatible objects store artifacts. Monorepo tooling is pnpm/Turborepo plus Cargo. Runtime patches are pinned by lockfiles; platform dependencies are qualified rather than guessed.

The first product is a modular application with separate controller/supervisor, API/worker and gateway processes where lifetime or scaling requires them. Do not introduce independent services per domain object. A message broker/stream service or workflow engine is deferred until measured pressure justifies it. If introduced it becomes the authority for its work; two schedulers never own the same workflow.

**R03 — Desktop trust boundary.** Render packaged UI with Node integration disabled, sandbox enabled, context isolation enabled, strict CSP, validated narrow IPC, sender/frame checks and bounded payloads. Keep privileged Electron APIs out of the renderer. Custom protocol handlers confine reads to packaged assets and reject traversal/symlink escape. No arbitrary navigation, popup, permission, download or external scheme is implicitly granted. Every untrusted preview, generated HTML/SVG or extension has a separate sandboxed surface without privileged bridge or product cookies. Network policy for previews blocks unauthorized loopback/private access, including redirects and DNS changes. Desktop process lifetime never owns task lifetime.

S0 has no privileged renderer IPC, preview or external navigation and can therefore omit an unused preload. The shell uses a private `conductor://app` asset scheme. File inspection, terminals, editors, LSP/DAP and preview permissions require later gates before activation.

## 3. Product objects and authority

**R04 — Domain ownership.** Model Task (desired goal), Attempt (one execution), Workspace (repository snapshot and writable checkout), Host (endpoint), Environment (immutable toolchain definition), Session (adapter conversation/PTY), Action, Approval, Artifact and IntegrationOperation separately. IDs are globally unique opaque identifiers and never confer authority. Every team resource binds tenant/project, with authorization repeated at use.

| Aggregate | Sole authoritative writer | Revision/command semantics |
|---|---|---|
| Local Task desired state and schedule | Origin host | Host task revision; remote publication is a projection |
| Team Task desired state/assignment | Coordinator | Postgres task revision; local UI changes route here |
| Attempt observed state | Assigned host controller | Attempt revision and ownership generation; cloud projects events |
| Process/session start and exit receipts | Supervisor | Session ID and launch digest; separate owned storage |
| Protected external-effect admission | Credentialed broker | Operation ledger serialized with ownership/policy changes |
| Terminal input | Supervisor | One writer lease, explicit takeover |
| Cache/UI preferences | Device | Cannot confer execution authority |

Publishing a local task cannot silently change authority. Promotion uses a quiescent transfer or creates a separately identified linked team task. A host-local emergency stop can terminate an attempt while disconnected, but does not overwrite team desired state. A new run then needs a separately authorized attempt. Task progress is derived; neither host nor coordinator races to write one shared status field.

**R05 — Attempt state and cancellation.** Attempt states are queued, provisioning, running, waiting_for_input, waiting_for_approval, validating, review_ready, completed, failed, cancelled, interrupted and outcome_unknown. Allowed progress is queued→provisioning→running; running↔waiting states; running→validating; validating→review_ready or failed; review_ready→completed after acceptance criteria. A revised change returns through running/validating with new evidence. Failure/cancel/interruption exits are available from nonterminal states. An unknown effect is explicitly reconciled; terminal attempts are not resurrected by replay. Retry creates a new attempt. Draft belongs to task intent, not a launched attempt. Agent “done” ends a turn, not verified completion. Cancellation requested and cancellation confirmed are distinct; cancellation never promises rollback of completed external effects.

## 4. Contracts, durability and transport

**R06 — Protocol evolution.** JSON Schema/OpenAPI define commands, actions, events and artifacts before endpoints expose them; generate or check language types and validate inputs at runtime. TS/Rust conformance vectors include valid and invalid cases. S0 implements only `health-v1.schema.json`; future envelopes below are requirements, not fake schemas or APIs. Capabilities are negotiated explicitly and default unavailable. Unsupported action/approval schemas fail closed. Unknown informational events may be skipped only with a snapshot-recovery path. Target additive client compatibility for 180 days, shortened for security when necessary; insecure runtimes are not supported merely because their protocol is compatible.

A command includes schema version, command ID, immutable payload digest, tenant/task/attempt target, expected aggregate revision, actor/device identity, deadline and operation. An event includes event ID, aggregate sequence, schema version, command/causation ID, actor, ownership generation and timestamp. Server derives identity/tenant from authenticated state; model-supplied identity never wins. Order is per aggregate. Use bounded WebSocket/binary framing for streams and separate bulk output from urgent control; HTTP handles ordinary commands. Client projections can resume from cursors or reload snapshots. No whole-database file sync or concurrent filesystem replication.

**R07 — Durable command semantics.** Persist a command before acknowledging `coordinator_stored`; transactionally persist host inbox/deduplication before `host_accepted`; separately record `effect_resolved`. Delivery is at least once. Repeated IDs with the same payload return the prior state; repeated IDs with changed payloads fail. Cloud acceptance can later become a durable host rejection for stale revision, expiry or changed permission. Queued-for-host never displays as running. State changes and outbox records commit in the same transaction. Critical SQLite state uses WAL + synchronous FULL on supported local storage; disk-full/I/O error prevents acceptance. Terminal scrollback can have a separate lossy policy.

Proposed remote command submission/replay horizon is 7 days; retain deduplication tombstones beyond the horizon. External-operation IDs survive for their reconciliation/retention period. A delayed old command remains expired after record cleanup. Older clients reload state and reconcile pending intent rather than relabeling old writes with a new ID. Credential/approval validity is rechecked at execution, never grandfathered from transport acceptance.

**R08 — Supervisor start and process ownership.** Supervisor API is idempotent `Start(session_id, launch_digest)` plus Query and Cancel. Persist launch intent, start/exit receipts and authenticated controller adoption identity. The same session ID cannot mean another launch. After lost responses query/adopt; a PID alone is not proof. If the OS spawn/persist crash window leaves execution unknowable, mark interrupted/outcome_unknown and do not relaunch without explicit new attempt authorization. Potentially executed terminal input is never resent automatically. The supervisor owns PTY and Windows Job handles, bounds output, controls child descendants, and reserves capacity for cancel/query during overload. Controller and supervisor schemas each have one migration owner.

**R09 — External effects and ownership fencing.** Broker alone holds credentials for strongly controlled publication. Atomically register a durable operation intent and validate ownership/policy before dispatch. Use stable provider idempotency and resource versions/conditional writes where supported. After ambiguous timeout reconcile provider state; unsupported non-idempotent uncertainty blocks automatic retry. Distinguish rejecting stale admission, deduplicating one operation and ordering conflicting resource writes. An ownership change cannot recall a dispatched request. Stop old admissions and reconcile outstanding operations before conflicting new writes; recovery may calculate on a separate branch while publication remains blocked. Strong publication/failover guarantees require an actually enforced boundary that keeps broker credentials and policy/operation stores inaccessible to the workload. A trusted CLI voluntarily using the broker is insufficient. Directly usable guest/provider credentials explicitly remove these guarantees and disqualify automatic protected failover.

## 5. Local, remote and platform lifecycle

**R10 — Lifecycle contract.** Closing a desktop window, normal UI Quit or UI crash leaves work with its supervisor while the interactive OS session survives. Expose a separate explicit Stop host operation. Controller update/restart adopts existing sessions. Supervisor updates drain; forced security interruption is visible and user-authorized under configured policy. Supervisor crash/reboot/logout interrupts the interactive profile; retain durable output/checkpoints and report uncertainty, not transparent process migration. Sleep suspends local compute and can break provider sessions; reconcile on wake. Uninstall stops owned work under a visible data retention/export policy. Unattended boot/session-independent operation is a separately enabled installation with separate credentials; never silently enable lingering or elevated services.

Use POSIX PTYs on Linux/macOS, ConPTY and Job Objects on Windows. Respect filesystem case, symlinks/reparse points, Unicode, executable bits, line endings and long paths. Tool discovery shows executable paths/version and environment profile; no implicit execution of untrusted shell startup files. WSL2 is a separately enrolled Linux host with repositories on its native filesystem. Native iOS/macOS builds require macOS capacity; Linux containers do not magically provide native Windows/macOS toolchains.

| Proposed primary target | Qualification boundary before GA |
|---|---|
| Linux desktop/owned host | Ubuntu 24.04/26.04 LTS x64; Wayland on both, X11 on 24.04; deb/AppImage; appropriate user service |
| Windows desktop/owned host | Supported Windows 11 x64 editions, 24H2 or newer; signed installer; native PowerShell/Git/ConPTY |
| macOS desktop/owned host | Apple Silicon, supported macOS 15+; signed/notarized app; launchd/Keychain |
| Android | Supported Android 12+ ARM64 devices compatible with chosen framework; Google-services devices primary |
| iPhone | Supported iOS 18+ devices compatible with chosen framework; signed App Store builds |

Minimums are product targets, not assertions of today's framework compatibility; raise them explicitly if native qualification requires it. Intel Mac, Windows ARM64, Linux ARM64/Fedora, WSL2 and Google-free Android are later qualified beta targets, not hidden primary requirements. Google-free Android relies on foreground inbox refresh. Primary OS families remain in scope if secondary targets are deferred. Linux update ownership is separate from Electron macOS/Windows updater support.

**R11 — Remote connection and revocation.** Hosts establish outbound authenticated connections; no unauthenticated inbound host listener. Use distinct user, approving-device, host, workload and integration identities/audiences. Enrollment binds account/tenant/public key to an expiring nonreplayable challenge; devices cannot choose their own role. OIDC/PKCE uses issuer/redirect/audience validation, rotated or sender-bound refresh credentials as supported. No shared organization-wide host master secret. Local IPC permissions protect against other users, not all malicious same-user programs.

Revocation prevents new authorized admissions and closes affected active streams/input leases. Already-dispatched effects can complete and require reconciliation. Show last observed host time and distinguish unknown/offline/asleep/provisioning/failed. A heartbeat timeout alone never starts a duplicate. Local-only trusted tasks retain local authority. Proposed managed offline computation grant is at most 15 minutes, renewable online; protected publication always needs online authority. Expiry survives suspension and clock changes; uncertain elapsed time, restart without trusted recovery or clock rollback fails closed for protected work. Device wall-clock time is not authoritative expiry. Handoff requires quiescence, a published checkpoint, input-lease revocation and source acknowledgement; unreachable source recovery is a visibly new attempt.

## 6. Mobile, previews and interaction

**R12 — Mobile functional parity.** Both phones support task creation on eligible hosts, attachments, inbox, summaries/paged logs, diffs/comments, clarifications, eligible approvals, cancel/steer and private previews. Advanced foreground terminal and tablets are optional refinements. Source/logic reuse does not mean DOM reuse. APNs/FCM are best-effort hints without source/secrets/approval tokens. Server inbox and foreground cursor catch-up provide correctness when notifications are denied, delayed, coalesced or absent. No continuous mobile agent or background socket requirement. Offline drafts/comments carry base revision, expiry and visible conflict/pending state; approval cannot queue silently while offline.

**R13 — Mobile authorization and storage.** Trusted native UI renders a canonical current Action, including organization, actor, host, repository, immutable inputs, destination, arguments, scope and expiry. Safely display Unicode/control characters, complete fields and truncation. Unknown schemas or effects that cannot be intelligibly reviewed on the phone require desktop review. Deep links only navigate. Refetch after resume and display durable receipt/rejection/pending status after submission; duplicate taps do not duplicate effects. Biometric user presence unlocks an approval key but is not proof of comprehension.

Use a qualified native encrypted SQLite layer covering WAL/temp data and attachments; cache keys and approval/device keys are separate. Approval keys require foreground user presence. Team source cache has a proposed maximum 24-hour offline-read grant, configurable shorter; sign-out/account switch clears authorized cache. Exclude sensitive cache/keys from device/cloud backups, conceal app-switcher snapshots, and explicitly handle biometric change, key loss, reinstall/restore and re-enrollment. Unsent drafts are not disposable cache and get visible retention/export/recovery. Revocation cannot erase a disconnected phone or previously exported content. S0 has none of these active surfaces and collects no credentials.

**R14 — Preview identity and isolation.** Desktop and mobile previews have no privileged bridge, product cookies or approval UI. Default-deny navigation/popups/downloads/external schemes and native/browser permissions. Remote preview routes bind tenant/user/workspace, host generation, namespace, service instance and route generation, not a reusable port. Single-use ticket redemption creates a scoped session; redact/suppress tokens from logs/referrers and never forward gateway authentication headers to the app. Use host-only cookies and origin/CSRF checks for HTTP/WebSockets, including sibling workspace origins. Separate product/content domains alone do not isolate sibling workspaces. Stop, reassignment and revocation invalidate routes. Authenticated browser automation is a separate coarse account-session/data-release grant, never falsely represented as per-tool enforcement of every website action.

## 7. Execution trust, workspaces and evidence

**R15 — Isolation profiles.** Label trusted host (effective authority of the OS account), restricted local (qualified container/VM) and isolated managed execution separately. A structured adapter is not a security boundary. All repository-derived execution, including agents, adapters, setup scripts, LSP/DAP, tools, tests and descendants, remains inside the declared profile's authority boundary. No silent fallback to trusted execution. Arbitrary CLIs expose only real sandbox/process controls, not invented per-command enforcement.

Trusted-host execution inherits account-accessible files, sockets, environment credentials and network access. It cannot claim protection from malicious same-user code or the resource-denial/egress guarantees below. The UI and capability report must disclose these limits before enabling this profile. S1 trusted execution does not require an unplanned sandbox, but process management, durable receipts and honest authority reporting still apply. R09's strong protected-publication guarantees apply only where its credential/policy boundary is independently enforced, never merely because a trusted CLI uses the broker.

For qualified restricted-local and isolated-managed profiles, workloads cannot reach host-control sockets, audit/policy stores, device keys, Docker sockets, SSH agents, metadata services or ambient credentials. The broker outside that enforced boundary exposes typed operations to an attempt-scoped identity that cannot impersonate the UI/approver. Enforce network policy outside the workload, including direct IP/DNS. Qualification must prove these exclusions on each supported profile/platform before advertising the isolation capability; otherwise the restricted profile is unavailable.

Linux namespace/cgroup/seccomp containers do not establish the strongest hostile-tenant boundary. Managed untrusted multi-tenant workloads use qualified VM/microVM isolation. Native macOS/Windows capacity is tenant-dedicated or reset from a verified clean image between trust domains; removing a checkout or stopping a process is insufficient. Revoke job credentials and discard profiles/caches. Snapshots cannot restore live approvals, secrets or execution leases. Privileged host/control-service compromise remains a declared trust assumption.

**R16 — Canonical action approval.** Define a versioned canonical serialization before enabling approvals. Bind schema, broker audience, tenant/actor/device, attempt/ownership generation, tool/executable implementation identity, cwd, effective environment policy, exact arguments, immutable input hashes, normalized resource/destination, policy revision, nonce and expiry. UI description and executed parameters derive from the same record. Broker consumption of a single-use approval and operation-intent registration are atomic. Snapshot mutable inputs or use race-safe handles; changed untracked files, scripts, environment or symlink targets invalidate relevant approval. A shell approval grants the disclosed execution-profile authority and resource scope, not a promise about arbitrary shell semantics or isolation absent from that profile. Allowed destinations can still leak data; constrain data release separately from hostname access.

**R17 — Repository and environment integrity.** Manifests record repository identity/base SHA, branch, environment digest, mounts, allowed setup, ports, platform/toolchain and secret references. Use worktrees for trusted parallelism, separate clone/snapshot and private Git metadata for untrusted jobs. No setup execution on opening an unknown repo. Confined Git/import helpers sanitize config/environment; disable hooks/fsmonitor/external diff/textconv/pagers, limit transports and avoid ambient credential helpers. Fetch/submodules/LFS/checkout are separately authorized. No global safe.directory wildcard. Restore validated objects/manifests rather than activating arbitrary .git config; extraction rejects traversal, device files, escaping links and Windows aliases/reparse points. Locks cover app-owned Git operations; detect/reconcile races from trusted external Git tools. Caches separate tenant and contribution/release trust domains plus lockfile/toolchain/OS/arch. OCI/Dev Container inputs are portable only on compatible execution targets.

**R18 — Artifact commit and access.** Artifacts bind tenant/project/task/attempt, producer identity/trust class, content hash/type, access and retention. Authorize upload/finalization, read, sharing, preview, indexing and restore; ID/hash possession grants no access. Avoid cross-tenant existence leaks in content addressing. Presigned URLs are short-lived bearer grants with explicit revocation delay; sensitive immediately revocable new reads go through an authorization gateway. Redaction is defense in depth; logs remain confidential.

Checkpoint states are creating→verified→published→cleanup_allowed. Upload immutable objects, verify complete contents, then commit manifest/reference/outbox. Automated destruction/transfer requires published checkpoint evidence; failed uploads preserve the source. Garbage collection follows references with orphan grace. Proposed defaults: local verbose logs 7 days, hosted verbose logs 30 days, compact change packages 180 days; tenant retention can override deliberately. Local-only host loss has no backup guarantee without configured backup/export. Use SQLite online backup, not live main-file copying. Export/import includes manifest, Git data, permitted blobs and environment description with credentials to rebind.

**R19 — Validation and integration.** A change package records base/candidate SHA, environment/platform, adapter/model version, executed check commands/results, skipped checks and provenance. Distinguish workload assertions from supervisor-observed exits and independently controlled validation jobs; workload hashes are not trusted attestations. Untrusted test code executes under its profile. Integration queues key by repo+target ref, apply onto current base and rerun required checks on the integrated candidate. Bound retries/starvation. Forge adapters respect branch protections and current review requirements. Editing code does not imply publication, messaging, merge or deployment authority. Auto-merge is separately configured against exact current candidate/checks. Historical validation is invalidated by relevant changes.

## 8. Agents, context and orchestration

**R20 — Replaceable adapters.** Adapter capability contract covers discovery/start/input/events/cancel, checkpoint/resume scope, tool requests and measured/estimated/unavailable usage. ACP is a supported adapter transport where available; MCP supplies tools/resources, not task authority. Preserve bounded private vendor diagnostics without polluting stable domain schemas. Resume declares same/new host, adapter version and session portability. Pin model/adapter per attempt. Provider fallback needs data-residency/release authorization. BYO subscription access follows provider entitlements and is not assumed equivalent to arbitrary API access.

**R21 — Context and memory.** Begin with Git/ripgrep/symbol/LSP/full-text retrieval; embeddings require measured benefit and replaceable index/model. Context has source revision/hash, time, access label and expiry. Authorization applies before retrieval and before provider submission. Source change invalidates stale summaries; deletion propagates to derived indexes and backups under retention. Task, project and personal memory are separate; model claims require evidence before promotion. Repo/web/MCP/skill content cannot grant permissions. No cross-tenant snippets, filenames or vector leakage.

**R22 — Scheduler and budgets.** Persist task DAG, dependencies, fair admission, concurrency/resource caps, deadlines, retry classes and maximum fan-out/depth. Agent plans are proposals; ordinary state machines own execution. Automations have timezone/DST/missed-occurrence policy, unique occurrence ID, revision, concurrency key and budgets. Default skip/coalesce backlog. Local schedule belongs to one host; team schedule to coordinator, with explicit transfer.

Budget escrow has unique allocations/nonoverlapping suballocations and reserved/committed/released/unknown states. Persist debit before chargeable admission. Disconnected or expired allocation stays encumbered until reconciled/conservatively settled; timeout cannot reallocate it. Recovery needs new funding. Reserve bounded maximum model input/output cost and compute duration; declare in-flight/shutdown/pricing overshoot envelope. Opaque CLIs without enforceable caps have soft estimates/time limits, never hard-dollar claims. Meter compute/storage/egress/model separately. Idle suspend respects resumability/artifact publication; independently enforced provider lifetime/emergency quotas limit orphan cost. Reconcile complete provider inventory including unknown resources and idempotency placement scope.

## 9. Operations, updates and release gates

**R23 — Identity, connectors and supply chain.** Store local secrets in supported OS stores with visible failure, hosted secrets under KMS/access separation. Never log tokens or persist them in argv/Git URLs. MCP rejects wrong-audience tokens; downstream credentials are separately scoped. OAuth discovery/redirects and tool URLs resist SSRF/DNS/redirect attacks. Plugins declare capabilities, run out of process/isolated UI surfaces, bind immutable payload hashes and require renewed admission for expanded capability. Initial mobile release excludes downloaded executable plugins.

Updates adopt TUF-style signed hash/length/platform/channel binding, freshness, anti-rollback, delegated keys, revocation/rotation and signed recovery releases. Isolate signing from untrusted PR execution, attach SBOM/provenance and separate release caches. Desktop/host/supervisor/adapter/schema compatibility is tested explicitly. One migration owner quiesces each schema; expand/contract changes respect old clients and active supervisors. A binary rollback cannot reverse new external effects or arbitrary data migration. Linux package/AppImage update paths have explicit ownership. Propose 48-hour triage/mitigation for actively exploited critical flaws, not a guarantee of third-party fixes.

**R24 — Recovery, privacy and observability.** Start with tenant home region, multi-zone Postgres, immutable object storage, API/worker/gateway replicas and separate execution capacity. Hosted team mode trusts its service with uploaded data; TLS/storage encryption are not E2EE. Local-only/self-hosted modes have explicit boundaries. Optional future E2EE requires its own key/recovery/search design.

Trace task/attempt/command/action IDs and timings with OpenTelemetry, without prompts/code/terminal contents by default. Redacted logs still get access/retention controls. Audit exports can use append-only retention; hash chains alone are not administrator-proof. Proposed targets before qualification: 99.9% hosted command acceptance, p95 home-region durable acknowledgement under 500 ms excluding provider/provisioning, p95 warm local navigation under 100 ms on published reference hardware; also measure connected-host delivery delay/queue age and phone diff/data/battery budgets. These are targets, not results.

Proposed managed recovery targets are RPO≤5 min and RTO≤1 hour, subject to drills; safety can require longer reconciliation. Restore starts write-frozen. Fence the old deployment, establish a nonreused recovery generation outside the restored snapshot or deliberately rotate/re-enroll credentials, invalidate old grants and reconcile lost intents/receipts, budgets, membership, manifests/objects/keys with hosts/providers before retries. Old restored counters cannot override live fencing. Missing revocation/consumed-approval state requires fresh authorization. Cloned workers get new identities. Unprovable external outcomes require operator reconciliation, not automatic replay.

## 10. GitHub development governance

**R25 — GitHub is the development system of record.** Follow the mandatory workflow in `docs/development-workflow.md` for every change: issue → isolated branch/worktree → draft PR → local and remote checks → three independent parallel expert approvals on the exact current head → eligible non-author GitHub approval → protected squash merge. Refresh reviews after changes; no fabricated reviewer identities, direct-main work, unilateral protection bypass or claimed merge without verification. Normative changes additionally require all three approval files bound to the new specification hash. Maintain accountable integration, evidence, ADRs and platform gates in GitHub. The one-time initial seed is allowed only after the full specification is unanimously approved; enforce/read back main protections immediately afterward. Governance settings and prose review are explicit controls with administrator/human trust limits, not cryptographic proof of agent independence.

## 11. Acceptance and implementation sequence

`docs/implementation-plan.md` maps every R01–R25 requirement to a release gate and falsification evidence. S0 scaffold completion requires reproducible install/lockfiles, TS check/tests/build, Rust fmt/clippy/tests, truthful health/unsupported endpoints, source for both phone targets, and explicit evidence gaps. Native builds, process survival, sandbox enforcement, encrypted caches, hosting, signing/distribution, SLOs and store qualification remain future work until tested.

S1 is a local runtime proof with crash-safe journal/supervisor reconciliation and one owned workspace; S2 is a bounded five-platform beta on owned hosts with authenticated remote/mobile control; S3 is separately gated managed Linux execution. Self-hosting/shared native pools/marketplace follow their own recovery/security gates. No quarterly date is a GA commitment. Initial 12-person planning allocation: 3 runtime/platform, 2 desktop, 2 mobile, 3 coordination/integrations, 2 release/reliability/QA, with design/security support. Reestimate after a six-week end-to-end proof.

All three independent expert roles must approve the same frozen specification hash. Reviewers preserve findings and write their own verdicts; authors cannot relabel REQUEST_CHANGES as approval. Any normative edit invalidates all prior approvals, requires a new review round and prevents `check:approvals` from passing until every role approves the new digest. Evidence that cannot be produced on the current host must be disclosed, not replaced by source checks or a forged passing native result.
